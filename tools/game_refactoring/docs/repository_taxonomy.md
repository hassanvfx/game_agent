# Repository Taxonomy

This document classifies the `game_refactoring` repository into core, operational, experimental, generated, and historical areas.

Its purpose is to make cleanup safer by separating what appears to be part of the reusable operator-pipeline system from what appears to be supporting baggage, history, or generated output.

## Classification rules

The categories below are documentation and cleanup aids. They do not change runtime behavior.

### Canonical core
Source-controlled files and directories that define the reusable pipeline, orchestration model, operator contracts, and main execution paths.

### Operational documentation
Documents that should explain the current intended system behavior and operator workflow.

### Active support inputs
Catalogs, fixtures, and asset libraries that may still be referenced by the current pipeline and therefore should not be deleted or moved without dependency verification.

### Experimental or lab material
Files and directories that appear to support dry runs, exploratory development, debug work, isolated experiments, or transitional scaffolding rather than the main reusable path.

### Generated or runtime artifacts
Outputs produced by executions, dashboards, logs, and machine-generated state that are useful for inspection but are not clean architectural sources.

### Historical memory
Decision logs and journals that preserve context and provenance but should not override current canonical documentation.

## Canonical core

These areas appear to define the main reusable operator-pipeline system:

- `scripts/`
- `configs/`
- `prompts/`
- `specs/`
- `styles/`

Important script entrypoints include:

- `scripts/creative_refactor_cli.py`
- `scripts/creative_refactor_runtime.py`
- `scripts/create_run.py`
- `scripts/prepare_inputs.py`
- `scripts/generate_task_packet.py`

- `scripts/run_operator_pipeline_game.py`
- `scripts/operator_registry_v2.py`
- `scripts/spec_adaptor.py`

These files should be treated as the main architecture surface unless a later refactor explicitly changes that.

## Operational documentation

These docs should describe the current system and should be kept aligned with the intended architecture:

- `README.md`
- `docs/operator_pipeline_manual.md`
- `docs/media_mapper_prompt_packet_spec.md`
- `docs/kill-all-operation.md`

These are the docs that should become the primary source for understanding the project.

## Active support inputs

These may feed operator stages or execution-time decisions and should not be removed blindly:

- `catalogs/`
- `assets/audio_library/`
- selected fixtures in `fixtures/`

Examples of likely active support content:

- `catalogs/audios.json`
- `catalogs/fonts.json`
- `catalogs/gifs.json`
- `catalogs/sprites.json`
- selected manifest fixtures used by CLI and operator-pipeline runs

Some support directories may also contain a mixture of active inputs and generated byproducts. Those should be split conceptually before any file movement.

## Experimental or lab material

These appear to be exploratory or transitional rather than canonical runtime surfaces:

- `fixtures/operator_pipeline_lab/`
- `fixtures/spec_adaptor_debug/`
- `fixtures/spec_adaptor_test_lab/`
- `fixtures/style_resolution_test_run/`
- `scripts/operator_pipeline_lab.py`

Likely mixed experimental areas:

- `catalogs/sprites/v2_prompt_optimize/`
- `catalogs/sprites/runs/`

These should be treated as quarantine candidates until dependency boundaries are confirmed.

## Generated or runtime artifacts

These are useful for debugging, auditability, and provenance, but they should not be treated as authoritative source material:

- `runs/`
- generated dashboard outputs
- generated launcher files
- execution logs
- state snapshots
- prompt optimization outputs and batch job byproducts

Generated material often contains old paths, old run IDs, and historical names. Those references should usually be classified rather than manually rewritten.

## Historical memory

These areas record prior work and reasoning, but they are not the canonical architecture source:

- `docs/journals/`

Journals are valuable for:
- tracing prior decisions
- understanding why a file exists
- recovering context from past tasks

Journals should not be used as the main authority for the current architecture when they conflict with top-level operational documentation.

## Naming cleanup guidance

Legacy naming references fall into different risk classes:

### Safe documentation cleanup
- human-facing repo identity text
- outdated explanatory wording
- stale references in current-facing docs where meaning is unchanged

### Review before editing
- helper scripts with path assumptions
- tests and fixtures with embedded historical strings
- style metadata derived from prior runs
- file names or comments that may still be useful provenance

### Defer unless doing a compatibility-reviewed code pass
- runtime identifiers such as `run_game_remixer_*`
- generated run trees
- temp/log naming patterns
- code symbols tied to orchestration behavior

## Recommended cleanup order

1. Rewrite canonical docs so they describe the intended architecture
2. Reclassify lab/generated/historical areas in writing before moving or deleting anything
3. Re-audit remaining repo-owned naming references
4. Only then decide whether any code-level rename or quarantine move is worth the compatibility risk

## Out of scope for this document

This taxonomy does not:
- prove runtime dependency boundaries
- authorize deletion of any directory
- rename code symbols
- rewrite generated run artifacts

It exists to reduce cleanup risk and make future repurposing work more deliberate.
